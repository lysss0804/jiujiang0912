## 1. 系统边界

### 1.1 本仓库覆盖的范围

```
供应商数据 → 规则引擎分级 → 维度归类 → Multi-Agent 协同分析 → 结构化报告
        → 处置门禁 →（问题较小：待供应商重新申报 / 其余：人工复核）
        → 【边界】后端按角色生成 PDF / 推送 / 权限校验 → 人工处置
```

`app/` 覆盖「规则引擎分级 → 维度归类 → Multi-Agent 分析 → 结构化报告 → 处置门禁」。

### 1.2 明确不在本仓库范围（后端职责）

| 事项 | 说明 |
| --- | --- |
| PDF 生成 | 本仓库只给 Markdown / HTML 模板与结构化 JSON，**不生成 PDF** |
| 通知推送 | 本仓库只给「该发给谁」（`delivery_audience`），不发消息 |
| 权限/用户数据库 | 本仓库只做**数据裁剪**（`audience`），不校验真实身份 |
| 风险报告落库 | 本仓库只返回 JSON，不建表 |
| 供应商门户 | 本仓库只提供 `/agent/redeclare` 受理端点 |
| 未来风险预测 | **已彻底移除预测链路**（`app/prediction/` 已空），系统只输出「当前风险」 |

### 1.3 四条不可越界的硬约束

1. **不做预测**——只输出「当前风险等级」，无未来风险字段；
2. **不自动处置**——所有 `candidate_actions.execution_status` 恒为 `PENDING_HUMAN_REVIEW`，
   后端**不得**依据报告直接自动停服/处罚/解约；
3. **不编造事件**——无数据来源的维度标 `data_status=NO_DATA` 计 0 分；
4. **门禁纯确定性**——「是否允许供应商重新申报」由规则判定，模型不参与，
   后端**不得自行放宽** `disposition.can_redeclare` 的结论。

## 3. 核心数据契约（后端最需关注的部分）

### 3.1 三个「版本号」不要混

| 版本常量 | 值 | 定义位置 | 含义 |
| --- | --- | --- | --- |
| `REPORT_SCHEMA_VERSION` | `C-DRAFT-V0.3` | `app/schemas/report.py` | 结构化报告 `risk_report` 的版本 |
| `OUTPUT_SCHEMA_VERSION` | `C-DRAFT-V0.2` | `app/schemas/output_contract.py` | 对外评测输出 / 人工审核记录的版本 |
| `rules.yaml::version` | `0.2.0-draft` | `app/rules/rules.yaml` | 分级规则版本（**换银行正式规则时改这里**） |

对应 Schema 文件（由 `python -m app.main export-contracts` 生成）：

```
docs/contracts/risk_report.C-DRAFT-V0.3.schema.json
docs/contracts/assessment_output.C-DRAFT-V0.2.schema.json
docs/contracts/human_review_request.C-DRAFT-V0.2.schema.json
docs/contracts/human_review_record.C-DRAFT-V0.2.schema.json
```

**改契约后必须重跑 `export-contracts`**，否则 Schema 与代码脱节。

### 3.2 `RiskReport` 十大分区（`app/schemas/report.py`）

| 分区 | 字段 | 说明 |
| --- | --- | --- |
| ① 基本信息 | `supplier_profile`、`supplier_id`、`supplier_name`、`current_week` | |
| ② 当前风险等级 | `risk_grade` | 含 `risk_level` / `score` / `grade_label` / `grade_range` / `hit_rules` / `window_*` / `importance_*` / `report_period` |
| ③ 六维度分布 | `dimension_breakdown[]` | 每条含 `dimension` / `event_count` / `score` / `data_status` |
| ④ 风险趋势 | `risk_trend` | `trend_type` / `trend_desc` / `trend_support_evidence_ids` |
| ⑤ 风险总结 | `risk_summary`、`key_factors[]`、`association_summary` | |
| ⑥ 风险证据 | `evidence_summary[]`、`evidence_by_dimension` | 可追溯，带 `evidence_id` |
| ⑦ 政策依据 | `policy_basis[]` | 含 `chunk_id` / `excerpt` / `vector_source` |
| ⑧ AI 分析与建议 | `rationale`、`recommendation`、`candidate_actions[]` | |
| ⑧.1 一致性校验 | `consistency_check` | 可为 `null`（未执行/降级） |
| ⑨ 人工处置 | `human_review_status`、`disposition` | 处置门禁结论 |

| ⑩ 运行信息 | `analysis_route`、`errors[]`、`audit_trace[]` | 审计可追溯 |

### 3.3 两个「等级」务必区分（后端展示最易出错之处）

| 概念 | 取值 | 来源 | 作用 |
| --- | --- | --- | --- |
| **供应商重要性**（两级） | `重要` / `一般` | `suppliers.csv::importance_level`（银行名单） | **只作分值系数**（1.2 / 1.0），不参与风险等级判定 |
| **风险等级**（三级） | `RED` / `YELLOW` / `GREEN` | 规则引擎按分值 + 档位表 | 最终结论 |

- 字段区分：`risk_grade.importance_tier` vs `risk_grade.risk_level`；
- 重要性来源：`importance_source` = `BANK_LIST`（银行名单，权威）/ `DERIVED`（名单缺失时系统推算）；
- **报告周期与风险等级无关**：`report_period` 由重要性决定（`重要 → weekly 周报`，`一般 → monthly 月报`）。

## 4. 接口层实现要点（`app/api/`）

### 4.1 统一响应信封（`app/api/envelope.py`）

```json
{ "code": 0, "message": "ok", "data": { ... }, "trace_id": "3f2c..." }
```

| code | HTTP | 触发场景 |
| --- | --- | --- |
| `0` | 200 | 成功 |
| `40000` | 400 | 请求非法（`DataValidationError`、重复 `run_id`） |
| `40100` | 401 | 未带/带错 `X-API-Key` |
| `40400` | 404 | 未知供应商 ID、未知 `task_id` |
| `42200` | 422 | 参数校验失败（`data.errors` 给明细） |
| `50000` | 500 | 未预期异常 |

**契约保证**：所有错误也走同一信封，`body` 永远可解析；HTTP 状态码与 `code` 语义一致。

### 4.2 异常处理链路（`server.py` 四个 handler）

| Handler | 捕获 | 转为 |
| --- | --- | --- |
| `RequestValidationError` | FastAPI 入参校验失败 | 422 / `42200`，`data.errors` 明细 |
| `ValueError` | 业务层校验（重复提交等） | 400 / `40000` |
| `ValidationError` | 模型内部跨字段校验（如 APPROVED 缺 `final_action`） | 422 / `42200` |
| `JiujiangError` | 领域异常（见下） | 按类型映射 code |
| `Exception` | 兜底 | 500 / `50000` |

`JiujiangError` 子类映射：`DataValidationError → 40000`、`UnauthorizedError → 40100`、
`UnknownSupplierError / UnknownTaskError → 40400`，其余 `50000`。

### 4.3 鉴权与链路追踪（`app/api/deps.py`）

- 鉴权：`API_KEY` 为空时**完全跳过**（方便本地联调与自动化测试）；配置后所有接口需带
  `X-API-Key`。生产环境务必配置并叠加内网网关 / IP 白名单；
- `trace_id`：优先沿用上游请求头 `X-Trace-Id`，否则自行生成 UUID；**建议后端落日志**，
  同时传 `X-Trace-Id` 便于跨服务串联。

### 4.4 异步任务（`app/api/task_store.py`）

- 触发条件：`async=true` **且为批量模式**（`supplier_ids` 数量 != 1）；
- 实现：**进程内内存字典 + 后台线程**（`threading.Thread`，daemon）；
- 返回：`{"task_id": ..., "status": "PENDING", "polling_url": "/agent/task/{task_id}"}`；
- 轮询：`GET /agent/task/{task_id}`，建议 1~2 秒一次；
- **限制（重要）**：服务重启后 task_id 全部丢失；多进程部署（多 worker）时各进程任务表**不共享**。
  生产必须替换为 Redis / 数据库 + 分布式锁，**接口签名不变**。

### 4.5 供应商 ID 归一化（易错点）

- 源数据使用**非断行连字符 U+2011**（形如 `S‑NOR001`），视觉上与 ASCII `-` 几乎无差；
- 服务端已归一化（`app/data/loader.py::normalize_supplier_id` / `resolve_supplier_id`），
  **后端直接传普通 ASCII 连字符即可**，两者都能命中；
- 但**返回体里仍是源数据原始 ID**（含 U+2011），后端比对/落库时注意先归一化。

## 5. 关键业务逻辑（后端需要理解，避免误用）

### 5.1 风险分级引擎（`app/rules/engine.py`，**纯确定性，无 LLM**）

**分值公式**：

```
单条事件分值 = severity_weights[严重度] × category_weights[维度] × time_decay[距当前周数]
维度得分     = 该维度所有事件分值之和
总分         = Σ维度得分 × 重要性系数 × 整改系数（整改期内 0.85）
```

**取档顺序**（`resolve_grade_tier`）：

1. **红线优先**：命中 `red_line_rules` 直接判 `RED`（当前红线仅 `RL-SEV-3`：窗口内出现严重度 ≥ 3 的事件）；
2. **有序取档**：按 `grade_tiers` 从高到低取第一个 `score >= min_score` 的档；
3. **多维度兜底**（可配）：命中维度数 ≥ `dimensions_hit_min_count`（默认 3）时至少提到 `YELLOW`；
4. 同时输出 `score` / `grade_tier` / `grade_label` / `grade_range` / `next_threshold_gap`。

**当前档位（本地数据标定，待银行正式规则替换）**：

| 档位 | 名称 | min_score | 分值标准 |
| --- | --- | --- | --- |
| `RED` | 高风险 | 2.0 | `[2.0, +∞)` |
| `YELLOW` | 中风险 | 0.8 | `[0.8, 2.0)` |
| `GREEN` | 低风险 | 0.0 | `[0, 0.8)` |

> 阈值是**数据不是代码**，随本地数据分布标定，保证三档都能触发。

### 5.2 统计窗口（`app/rules/window.py`）

- 请求可传 `window_unit`（`week` / `month`）与 `window_size`；
- **1 月 = 4 周**（`WINDOW_WEEKS_PER_MONTH` 可配），内部统一归一化为**周区间**，
  全链路只有一套口径；
- 优先级：**请求入参 > Settings > rules.yaml > 内置默认**；
- 不传时等价于「近 12 周」（向后兼容）；
- 归一化结果写入报告：`window_unit` / `window_size` / `window_weeks` / `window_display`
  （如 `近12周` / `近3个月（第41-52周）`）。

### 5.3 处置门禁（`app/agents/human_review.py::judge_disposition`）

**完全确定性，模型不参与**。优先级：

| 处置态 | 触发条件 | `can_redeclare` |
| --- | --- | --- |
| `EVIDENCE_INSUFFICIENT` | 证据门禁未通过（**优先级最高**） | `false` |
| `AWAITING_SUPPLIER_REDECLARE` | 风险等级为中/低档 **且** `score <= 0.8` **且** 无红线 **且** 最高严重度 < 3 | `true` |
| `PENDING_HUMAN_REVIEW` | 其余情况 | `false` |

配套字段 `disposition.reason` 给出中文原因，**可直接展示给审核人**。

### 5.4 横向对比数据块（`app/batch/service.py::build_cross_supplier_comparison`）

- **纯计算，无模型调用**；由批量结果产出，供后端渲染「横向对比 PDF」；
- 内容：`level_distribution`（等级分布）/ `dimension_baselines`（逐维度中位数基线）/
  `rankings`（逐家分值与中位数偏差、排名）/ `median_score` / `note`；
- **`audience=MANAGER` 时该字段被置为 `null`**，并追加 `cross_supplier_comparison_withheld` 说明；
- 单供应商分析时该字段恒为 `null`。

### 5.5 重点监测名单排序规则

`watchlist` 按 **(风险等级, 得分)** 降序：`RED → YELLOW → GREEN`，同级内得分高者在前。

## 6. 大模型链路与降级语义（**必须理解，否则会误判"报告质量"**）

### 6.1 确定性优先原则

| 不交给 LLM（全部 Python 确定性） | 交给 LLM（仅自然语言文案） |
| --- | --- |
| 阈值判断、风险等级计算 | 风险总结 `summary` |
| 六维度评分与统计 | 趋势解读 `trend_desc` / 跨维度说明 |
| 时间窗口过滤 | 证据可读转述 `readable_summary` |
| 证据归属与时间校验 | 决策 `rationale` / `recommendation` |
| 趋势类型判定、排序、grounding 校验 | 一致性校验 `notes` / `conflicts` |

> **一句话**：所有数值、枚举、分级、字段归属都由确定性代码产出；LLM 只把事实翻译成自然语言。

### 6.2 节点级开关（`enable_live_llm=true` 时生效，默认全开）

| 环境变量 | 作用节点 |
| --- | --- |
| `LLM_DIMENSION_MAPPING` | 维度归类（**一次调用批量返回**） |
| `LLM_TEXT_RISK_IDENTIFICATION` | 风险识别总结 |
| `LLM_TEXT_ASSOCIATION` | 关联分析趋势 / 跨维度说明 |
| `LLM_TEXT_EVIDENCE` | 证据转述（**一次调用批量返回**） |
| `LLM_CONSISTENCY_CHECK` | 多智能体一致性校验 |

### 6.3 四种状态标记

| 标记 | 含义 |
| --- | --- |
| `SUCCESS` | 模型调用成功并通过结构化校验，报告使用模型文案 |
| `FALLBACK` | 模型不可用/输出不合法/越界引用，已回退确定性模板 |
| `DISABLED` | 节点开关关闭或 `enable_live_llm=false` |
| `SKIPPED` | 前置条件不满足（如证据门禁未通过时的一致性校验） |

> **核心契约**：**任何模型异常都不会使接口失败**，最坏情况全部 `FALLBACK`，
> 字段结构与取值域**不变**，报告**始终可生成**。
> 后端**不要**把 `FALLBACK` 当作错误，它是设计内的降级路径。

### 6.4 Grounding 与合规拦截

| 防线 | 实现位置 |
| --- | --- |
| 引用越界（编造 `evidence_id` / `chunk_id`） | `app/agents/helpers.py::require_grounded`，越界即抛错→降级 |
| 建议越界（自动停服/处罚/解约） | `app/agents/decision.py::_validate_candidate_actions`，命中黑词即降级 |
| 关键因素抄提示词模板 | `_normalize_key_factors` 剔除占位并用规则事实回填 |
| 建议优先级与等级矛盾 | `_normalize_priority` 按等级强制对齐（禁止高风险标低优先级） |
| 输出结构不合法 | Pydantic `StrictModel`（`extra="forbid"`）严格校验 |

### 6.5 RAG 向量来源（`vector_source`）

| 取值 | 触发条件 |
| --- | --- |
| `hash` | 未配置 embedding（默认），用本地 sha256 伪向量，零外部依赖 |
| `embedding` | 配置了 `EMBEDDING_MODEL`（或复用对话模型且非 mock） |

> **切换 embedding 后务必重建索引**（`python -m app.main rag-demo`）。
> 索引向量维度与查询侧不一致时相似度无法计算，会退化为「按原顺序返回」。
> 真实 embedding 调用失败时自动回退 `hash`，检索不中断。
> `PolicyBasis.vector_source` 字段保留，供后端审计「政策依据是否真实语义检索命中」。

## 12. 历史缺陷备忘（后端自查清单）

以下为本项目在真实数据 / 真调模型下**已修复**的缺陷，后端对接时可据此自查：

| 曾经的问题 | 表现 | 现状态 |
| --- | --- | --- |
| 决策节点用模块级导入工厂 | 测试注入的假客户端被绕过，节点**真实打网** | 已改为运行时经 `llm_factory.build_llm_client` 解析 |
| 合规约束只写在提示词 | 模型建议「自动停服」时**全程无拦截** | 已加 `_validate_candidate_actions` 显式校验 |
| 关键因素抄回占位模板 | 报告出现「命中规则 R-XXX：<规则描述>」 | 已加占位检测 + 规则事实回填 |
| 政策检索恒为空 | 向量维度不一致时 0 分被当作「无结果」过滤，决策永远走兜底 | 已改为按分数降序取 top_k |
| `EMBEDDING_DIMENSIONS` 配置失效 | 配置项与文档均存在，但代码写死 256，从未读取 | 已由 `build_rag_service` 透传 |
| 趋势正文被丢弃 | 模型生成的 `trend_desc` 渲染时整段消失 | Renderer 已兼容扁平与嵌套两种口径 |
| `disposition` 不进最终状态 | LangGraph 只保留 TypedDict 声明过的 key | 已在 `WorkflowState` 显式声明 |
| 字段名与节点名重名 | 与 LangGraph state channel 冲突 | 已统一改为 `*_result` 后缀 |
